# Prompt Cache TTL 支持方案（plan1）

- 日期：2026-11-12（第四稿：与机器、模型无关的总纲；加入与 Kimi 对齐的验收标准）
- 范围：单机、单实例（多卡 TP）的推理服务，支持 5m / 1h 两档缓存 TTL
- 状态：设计稿，未写代码。SGLang 部分基于 0.5.20 源码阅读；vLLM 部分待验证
- 前置：已有一版 v0.4 TTL 实现（`compat/cache_ttl.py`、`compat/cache_hooks.py`，说明见 `docs/cache-v040.md`），本方案是在它之上的第二版

本文是总纲，不绑定具体模型和机器。所有容量相关的内容都用参数和公式表达，落地到某个部署时代入该部署的实测值。附录 A 给了两个算例，仅作示意。

文中结论的来源分三类：**已核实**（读过源码）、**推断**（由已核实的事实推出，未直接测量）、**待确认**。

## 1. 目标

对外提供和 Kimi / Anthropic 官方一致的缓存 TTL 语义：

1. 有效期内命中，按缓存命中计费。
2. 过期后不算命中，按未命中（缓存写入）计费，返回字段与未命中一致。
3. 命中即续约，有效期从命中时刻重新计算。
4. 支持 5m 和 1h 两档；不传时默认 5m。
5. **验收目标**：与 Kimi 的缓存机制一致，语义对齐、字段对齐，依据是 [Kimi 上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)。内部"过期但数据仍在则直接复用"的行为保留，但客户不能通过任何返回字段感知到差异。验收标准见第 5 节。

内部目标：

- 尽量少做重复的 prefill 计算。
- TTL 机制本身不拖慢推理。
- 缓存数据的物理留存时间有明确上限。

### 已定的四项决定

| # | 问题 | 决定 |
|---|---|---|
| 1 | 不传 TTL 时 | 对齐 Kimi 官方，默认 5m |
| 2 | 不同档位命中同一份有效缓存 | 首次写入锁定档位 |
| 3 | 过期后内部复用的计费 | 按未命中计费，返回字段符合未命中 |
| 4 | 物理留存上限 | 结合吞吐和磁盘空间设计，见 4.8 |

## 2. 整体策略与思想

### 2.1 核心思想：物理状态和计费状态分离

一份 KV 缓存有两个互相独立的状态：

| 状态 | 含义 | 由谁决定 |
|---|---|---|
| 物理状态 | KV 数据还在不在（L1 / L2 / L3） | 容量、淘汰策略、留存上限 |
| 计费状态 | 对用户算不算命中 | TTL 租约 |

以条目"最后一次被使用"的时刻为起点，按空闲时长分成三段：

| 空闲时长 | 物理 | 计算 | 对用户 |
|---|---|---|---|
| 小于 TTL | 可用 | 跳过 prefill | 命中 |
| TTL 到留存上限之间 | 可用（如果还没被容量淘汰） | 跳过 prefill | 未命中，按写入计费，并重新建立租约 |
| 超过留存上限 | 不可用，等待清除 | 重新计算 | 未命中，按写入计费 |

第二段是本方案相对 v0.4 的主要变化：**过期不等于删除**。过期数据只要还在、且没超过留存上限，推理系统就直接复用，只是对用户报告未命中。输出不受影响，因为复用 KV 和重算在数值上等价。

### 2.2 语义规则

1. **有效期内命中**：从请求开头起、连续且租约有效的那一段前缀，算计费命中。
2. **过期不命中**：到期判定用 `now >= expires`。过期部分按写入计费。
3. **命中续约**：只续约本次请求实际采用的前缀。只是探测、还在排队的请求不续约；兄弟分支和没用到的长尾不续约。（沿用 v0.4）
4. **默认档位**：请求不带 TTL 时按 5m 处理。所有请求都走 TTL 路径，不再有"不过期"的原生路径。
5. **首次写入锁定档位**：
   - 租约有效期内档位不变，命中按原档位续约，与本次请求传的档位无关。
   - 在一段有效前缀后面新增的页，继承该前缀的档位。（Kimi 文档："新增部分也按锁定的 TTL 继续写入"）
   - 只有前一页已过期或不存在时，新页才采用本次请求的档位。
   - 效果：请求传 1h、但命中的是一段有效的 5m 前缀时，整条链仍是 5m，写入量记在 5m 字段里。要换档只能等它完全过期。
6. **活动请求不受影响**：已经采用缓存的请求继续用自己的状态，不会中途被清空。（沿用 v0.4）
7. **TTL 是软承诺**：容量压力下数据可能在有效期内被淘汰，之后正常重算。

### 2.3 一份有效期状态，三级共用

有效期是条目的逻辑属性，不属于某一层。L1、L2、L3 共用一张**租约表**：键是页的链式哈希，值是"最后使用时间"和"档位"。数据在层间移动时租约不变。

它不挂在前缀树节点上，原因是（已核实）SGLang 在 L2 淘汰时会把节点从树里删除，而且树不保存 L3 的元数据。

由"最后使用时间"可以同时算出两件事：

- 租约是否有效：`now < 最后使用时间 + TTL`
- 是否允许物理复用：`now < 最后使用时间 + 留存上限`

租约表里查不到的页，一律视为超过留存上限、不可复用。因此记录可以提前清理（效果只是少复用一次），进程重启后表为空也是安全的。

### 2.4 分层策略

| 层 | 介质 | 策略 |
|---|---|---|
| L1 | GPU 显存 | 原生 LRU，不变 |
| L2 | 主机内存 | 超过留存上限的最先淘汰，其次是租约已过期的，其余按 LRU |
| L3 | 本地 NVMe | 只接收"1h 档、租约有效"的条目，后台提前写入，受每日写入预算限制 |

**5m 档不写 L3**。条目被挤到 L2 队尾时，如果是 5m 档或租约已过期就直接丢。

**写 L3 的时机**：后台提前写，不等到淘汰那一刻。

- 触发信号：L2 的 LRU 队尾区域内，存在"1h 档、租约有效、未备份"的数据。**不能用占用率做触发**，缓存稳态下永远是满的，占用率恒为 100%。
- 队尾区域大小：覆盖未来 1～2 分钟的淘汰量。
- 写入条件：1h 档；租约剩余时间大于下限（建议 5 分钟）；长度不小于 L3 预取阈值（默认 256 token）；当日写入预算未用完。
- 来不及或预算用完时：直接丢弃并计数。

写入量的上限是 L2 的淘汰速率，不是占用率，所以不会"一直写"。

### 2.5 时钟与一致性

多卡 TP 下每个 rank 是独立进程，各有一棵前缀树，必须做出完全一致的决策。

规则：**rank 0 是唯一的时钟和租约权威**，其他 rank 的本地时钟不参与任何决定。（沿用 v0.4，已核实它用 `dist.broadcast_object_list` 广播查找长度）

本方案多广播一个时间戳，各 rank 用同一个"当前时间"维护各自的租约表副本。淘汰排序、写 L3、留存清除都读这份副本，各 rank 结论一致。

（已核实）前缀树节点自带的 `last_access_time` 是逻辑计数器（每次加 1.0），不是真实时间，不能用来判断过期，必须另记广播来的时间戳。

时间水位单调不减，系统时钟回拨不会让已过期的租约复活。（沿用 v0.4）

### 2.6 隔离与对外可见性

- **隔离**：过期数据的内部复用限定在同一个隔离域内（`cache_salt` / extra key）。（已核实）SGLang 原生的页哈希以 `extra_key` 和 `cache_salt` 为种子，天然按隔离域区分。
- **对外可见**：过期复用时，所有返回给用户的字段都按未命中填写（见 4.5）。延迟会比真正的未命中短，这一点无法隐藏。
- **留存**：对外措辞为"至少保留 TTL 时长"；内部以留存上限为硬边界，超过后既不复用也不保留（见 4.8）。

### 2.7 容量模型

TTL 能不能守住、要不要 L3、L3 该多大，都由下面几个参数决定。它们因部署而异，需要实测。

| 符号 | 含义 | 来源 |
|---|---|---|
| C2 | L2 容量（token） | 配置 |
| S3 | L3 配额（字节） | 配置 |
| b | 每 token 的 KV 字节数（所有 rank 合计） | 实测 |
| R | 新 token 流入 L2 的速率（token/秒） | 实测 |
| f | 1h 档流量占比 | 实测 |
| V | L3 所在磁盘的容量 | 硬件 |
| D | 磁盘耐久等级（每日全盘写入次数） | 厂商规格 |
| T_keep | 物理留存上限 | 本方案设定 |

**L2 周转时间**：L2 满的时候，淘汰速率约等于流入速率，所以

```
T2 = C2 / R
```

条目被挤到 L2 队尾时，大约已经空闲了 T2。这是上限估算：被反复命中的老条目也占空间，实际会更短。

由此得到两个流入速率门槛：

| 门槛 | 含义 |
|---|---|
| R < C2 / 3600 | L2 自己能撑住 1 小时。被淘汰的条目都已过期，L3 基本不写 |
| C2 / 3600 < R < C2 / 300 | L2 撑不住 1 小时，1h 档依赖 L3 |
| R > C2 / 300 | L2 连 5 分钟都撑不住，5m 档开始违约 |

**L3 的三个约束**。设 L3 的写入速率为 W3（token/秒），最坏情况 W3 = f · R：

| 约束 | 条件 |
|---|---|
| 空间 | W3 · b · T_keep ≤ S3 |
| 寿命 | W3 · b · 86400 ≤ D · V · L3 份额 |
| 带宽 | W3 · b 远小于磁盘的持续顺序写速度 |

三者中哪个最紧取决于 b：b 越大，寿命约束越先到。寿命约束给出 L3 写入速率的上限：

```
W3_max = D · V · L3 份额 / (86400 · b)
```

**1h 档有容量保障的条件**：`f · R ≤ W3_max`。不满足时，预算用完后的 1h 条目会被丢弃，表现为违约率上升，解决办法是加盘、加内存或换耐久等级更高的盘。

要不要接 L3 的判断方法：先测 R，和 C2 / 3600 比较。附录 A 的两个算例显示，不同部署下结论可以完全相反。

## 3. 与现有 v0.4 实现的差异

v0.4 的做法（已核实）：把 TTL 秒数编码进 `cache_salt`；用 SQLite 记录每页的到期时间；匹配前按租约截短查找 key，过期部分不允许从任何一层命中。

| 方面 | v0.4 | 本方案 | 原因 |
|---|---|---|---|
| 过期后的物理数据 | 禁止命中，重新计算 | 留存上限内内部复用，只在计费上算未命中 | 减少重复 prefill |
| TTL 与隔离域 | TTL 编进 `cache_salt`，不同档位各占一个命名空间 | TTL 是租约表里的状态 | 同一内容不再按档位各存一份；实现档位锁定 |
| 不传 TTL | 走原生路径，不过期 | 默认 5m | 决定 1 |
| 匹配时截短 key | 截到租约有效长度 | 截到留存上限允许的长度 | 物理复用范围变大，但仍有边界 |
| 用量统计 | 原生统计，适配器不改 | 物理命中和计费命中分开，对外只报计费 | 决定 3 |
| 租约存储 | SQLite，WAL + `synchronous=FULL`，仅 rank 0 | 内存表，各 rank 一份副本 | 见下方说明 |
| 持久化 | 重启后保留有效期 | 默认不持久化 | 表为空是安全的 |
| 淘汰 | 原生 LRU | 超上限优先，过期其次，其余 LRU | 让无用数据先腾位置 |
| 写 L3 | 原生策略，不看 TTL | 只写 1h 档有效的，后台提前写，有写入预算 | 控制写入量和磁盘寿命 |
| 物理留存 | 不限，交给容量回收 | 有硬上限和清除机制 | 决定 4 |

**保留 v0.4 的部分**：按链式页哈希记租约；rank 0 权威加广播；只续约实际采用的前缀；探测不续约；活动请求保留自己的状态；时间水位单调；`prompt_cache_options` 的解析和校验；匹配、预取两处的截短 hook（截短长度的含义变了）。

**关于 SQLite（推断，未实测）**：v0.4 每次查找都在事务里更新时间水位，而连接设置了 `synchronous=FULL`，所以每次缓存查找都会触发一次落盘同步。改成内存表可以把这一项从请求热路径上拿掉。

## 4. SGLang 实现细节

源码依据：SGLang 0.5.20。下文路径相对于 `python/sglang/srt/`。落地到其他版本时，涉及具体函数的地方需要重新对照。

### 4.1 请求入口

沿用 v0.4 的解析和校验（正整数加 `s/m/h/d`，非法值返回 400），改动：

- 不再把 TTL 编码进 `cache_salt`，TTL 秒数作为请求的独立字段传给调度器。
- 不带 TTL 的请求填默认值 5m。
- 对外只开放 `5m` 和 `1h` 两个值（与 Kimi 一致），其他值返回 400。
- Anthropic 兼容接口的顶层 `cache_control: {"type": "ephemeral", "ttl": "1h"}` 映射到同一个字段；消息体内的同名标记忽略（与 Kimi 一致）。

### 4.2 租约表

```
键：原生的页链式哈希（即 node.hash_value 里的每一项，也是 L3 的对象键）
值：(last_used, ttl_seconds)
```

- （已核实）原生哈希由 `mem_cache/utils.py` 的 `get_storage_hash_str` 计算：以 `storage_namespace_seed(extra_key, cache_salt)` 为种子逐页链式哈希。它已经覆盖隔离域，可以直接当租约键，不需要 v0.4 自己的 `page_keys`。
- 匹配时节点还不存在，用同一个函数对请求的 token 序列算出各页的键。
- 只覆盖完整的页，不足一页的尾部不进租约表，计为普通输入。
- 内存字典，每个 rank 一份，由 rank 0 的广播驱动，保持逐条一致。
- 记录保留到 `last_used + T_keep`，之后清理。行数上限约为三层合计的 token 数除以页大小。

### 4.3 匹配：三个长度

1. rank 0 对请求各页查租约表，得到两个长度：
   - **计费长度**：从头开始连续"租约有效"的页数 × 页大小
   - **可复用长度**：从头开始连续"未超留存上限"的页数 × 页大小（不小于计费长度）
2. rank 0 把 `(计费长度, 可复用长度, now)` 广播给所有 rank。
3. 所有 rank 把查找 key 截到可复用长度，再调原生 `match_prefix`，得到**物理长度**。
4. 最终计费命中 = min(计费长度, 物理长度)。

截短的做法和 v0.4 相同（`match_prefix`、`_compute_max_prefix_len`、`_prefetch_kvcache` 三处 hook），只是截短长度从"租约有效"换成"可复用"。L3 预取同样受这个长度限制，保证超过留存上限的旧文件读不回来。

命中会续约整条已用路径，祖先的最后使用时间不早于后代，所以两个长度都天然是连续前缀。

### 4.4 续约与写入

时机沿用 v0.4：

- **续约**：`ScheduleBatch.prepare_for_extend` 更新真实缓存使用计数之后，只处理实际采用的前缀。
- **新页登记**：checkpoint 的 `insert` 成功之后。

对实际采用或新计算的每一页，按顺序处理（"前一页"指链上紧邻的上一页）：

| 页的状态 | 动作 | 档位 | 计费 |
|---|---|---|---|
| 租约有效 | `last_used = now` | 保持原档位 | 命中 |
| 租约过期但物理复用；或新计算 | 新建记录，`last_used = now` | 前一页租约有效则继承它的档位，否则用本次请求的档位 | 写入，记到所得档位 |

`now` 一律用 rank 0 广播的值。

### 4.5 用量上报：字段必须符合未命中

每个请求产出：

- 缓存读取 = 计费命中长度
- 缓存写入（5m）、缓存写入（1h）= 按 4.4 得到的各档位写入页数 × 页大小
- 普通输入 = 不足一页的尾部

**原则：凡是返回给用户的字段，一律用计费口径；物理口径只进内部指标。** 过期复用的部分在读取字段里是 0，在写入字段里按所得档位计数。

对外字段（与 Kimi 文档一致）：

| API | 缓存读取 | 缓存写入 |
|---|---|---|
| Chat Completions | `usage.prompt_tokens_details.cached_tokens` | `usage.prompt_tokens_details.cache_write_tokens` |
| Responses | `usage.input_tokens_details.cached_tokens` | `usage.input_tokens_details.cache_write_tokens` |
| Messages | `usage.cache_read_input_tokens` | `usage.cache_creation_input_tokens`，以及 `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` |

- Chat Completions 和 Responses：读取、写入、未缓存三者互斥，之和等于总输入。
- Messages：`usage.input_tokens` 不含读取和写入部分。
- Chat Completions 另加响应头 `Msh-Usage-Cache-Write-Tokens-5m` 和 `Msh-Usage-Cache-Write-Tokens-1h`。
- 流式请求在最后一个 chunk 的 usage 里给出完整明细。

（已核实）0.5.20 里的数据通路和要改的位置：

| 位置 | 现状 | 改动 |
|---|---|---|
| `managers/scheduler_components/output_streamer.py` | 按请求收集 `cached_tokens` 和 `cached_tokens_details`（按 device / host / storage 分来源） | `cached_tokens` 改填计费命中；新增两档写入量；分来源明细也只统计计费命中的部分 |
| `managers/io_struct.py` 等传输结构 | 携带上述两个字段 | 增加写入量字段 |
| `entrypoints/openai/serving_chat.py`、`protocol.py` | 从 `meta_info["cached_tokens"]` 组装 usage | 增加 `cache_write_tokens` |
| `entrypoints/anthropic/serving.py` | 只填 `cache_read_input_tokens` | 增加 `cache_creation_*` 字段，`input_tokens` 扣除写入部分 |

要特别注意分来源明细（`return_cached_tokens_details` 打开时返回）：如果不处理，它会把物理命中暴露给用户。

### 4.6 淘汰

（已核实）树核心持有一个可插拔的淘汰策略对象（`unified_cache/unified_tree_core.py` 里的 `self.eviction_strategy`，由 `get_eviction_strategy` 创建），每个策略只返回一个排序键，值小的先淘汰。

新增一个策略，排序键为 `(等级, last_access_time)`：

| 等级 | 条件 |
|---|---|
| 0，最先淘汰 | 超过留存上限（租约表里查不到） |
| 1 | 租约已过期，仍在留存上限内 |
| 2 | 租约有效 |

等级判断读本 rank 的租约表副本和广播来的 `now`，各 rank 结果一致。

**待确认**：L2 侧的淘汰走各组件自己的 `drive_host_eviction`，它是否使用同一个策略对象的排序键，需要读 `unified_cache/components/` 下的代码。

### 4.7 L3 写入

（已核实）现状：

- 写策略是全局开关 `--hicache-write-policy`（`write_through`、`write_through_selective`、`write_back`），不区分请求。
- `write_backup_storage(node_id)` 可以对任意一个在 L2 的节点发起写 L3；写入期间给节点加主机侧的锁，写完才释放。
- 自带多种 L3 后端，包括本地 `file`。单机场景用本地文件后端即可，不需要分布式存储。

新增一种按节点判断的写入逻辑：

1. 周期性检查 L2 的 LRU 队尾区域。
2. 对满足 2.4 写入条件的节点调用 `write_backup_storage`，并从当日写入预算里扣除。
3. 淘汰时：已备份的直接释放内存；未备份的直接丢弃并计数。
4. 从 L3 读回 L2 之后，不删除 L3 上的副本，避免之后再次被淘汰时重复写盘。

注意点：

- 写入期间节点不能淘汰，队尾区域要留足提前量。
- 触发条件只读逻辑状态（已用页数、租约表、预算计数），不读"某次写入是否完成"这类事件，保证各 rank 一致。
- KV 按 rank 切分时每个 rank 各写自己的一份，合起来才是完整的一页，取回时缺一不可。各 rank 持有相同完整副本的模型，原生只让一个 rank 回写。
- L3 目录按镜像摘要、模型版本、启动参数分命名空间（沿用 v0.4），不同配置不混读。

### 4.8 物理留存上限

#### 定义

留存上限 `T_keep`：一页 KV 自最后一次被使用起，最多允许存在和被复用的时长。三层共用一个值。

它是上限而不是保证。实际留存时间还受容量限制，是下面几项中最短的一个：

| 层 | 实际留存时间 |
|---|---|
| 内存（L1 + L2） | min(T_keep, C2 / R) |
| 磁盘（L3） | min(T_keep, S3 / (W3 · b)) |

#### 取值规则

| 参数 | 规则 | 默认 |
|---|---|---|
| `T_keep` | 最长 TTL + 过期复用窗口 | 2 小时（1 小时 + 1 小时） |
| 每日写入预算 | D · V · L3 份额 | 耐久等级未知时按 D = 1 |
| L3 写入速率上限 | W3_max = 每日写入预算 / (86400 · b) | 由上一项导出 |
| L3 配额 S3 | W3_max · b · T_keep，即 每日写入预算 × T_keep / 24 小时 | 由上两项导出 |
| 磁盘最低空闲 | 按盘上其他用途留余量 | 部署时定 |
| 预算形式 | 令牌桶，按小时均摊，允许短时突发 | — |

说明：

- **L3 配额由寿命预算和 `T_keep` 共同决定。** 在寿命允许的写入速率下，`T_keep` 时间内最多能写这么多数据；超过上限的会被清除。配额比这个数更大没有意义。
- **`T_keep` 的过期复用窗口取多长**，取决于"用户过期后多久回来"的分布。默认 1 小时，上线后看"命中时条目已空闲多久"的直方图调整（见 4.10）。窗口越长，省的计算越多，占的 L3 配额也越多。
- **L3 与其他数据共用一块盘时**，寿命和空间都要按份额分，不能按整盘算。

#### 各种负载下谁是瓶颈

| 条件 | 结果 |
|---|---|
| R < C2 / 3600 | L2 够用，L3 基本不写，留存由 `T_keep` 决定 |
| R > C2 / 3600 且 f · R ≤ W3_max | 1h 档靠 L3 保住，写入在寿命预算内 |
| f · R > W3_max | 预算用完后 1h 档部分违约；需要加盘、加内存或换更耐写的盘 |
| R > C2 / 300 | 5m 档也开始违约 |

#### 执行机制

留存上限靠三道措施保证，第一道保证"不再使用"，后两道保证"不再存在"：

1. **匹配时拒绝**：查找 key 截到可复用长度（4.3），超过上限的数据即使还在也不会被用到。这一条是即时生效的硬保证。
2. **淘汰优先**：超过上限的节点在淘汰排序里排最前（4.6）。
3. **定时清除**：后台任务周期性（建议每 5 分钟）处理：
   - L1 / L2：释放等级 0 的节点。
   - L3：删除超过上限的对象文件。判断依据是租约表；租约表里没有的文件（例如重启后的残留）按文件修改时间判断，超过 `T_keep` 即删除。

因此数据的最长存在时间是 `T_keep` 加一个清除周期。

#### 进程重启

重启后租约表为空，L1 和 L2 也是空的，L3 上的残留文件全部视为不可复用，由定时清除删掉。行为简单且严格。

可选增强：定期把租约表异步快照到磁盘（不在请求路径上同步落盘），启动时加载并丢弃已超上限的记录。这样重启后 L3 里仍有效的 1h 缓存可以继续用。是否需要，看重启频率。

### 4.9 多 rank 一致性清单

| 决策 | 权威 | 传播方式 |
|---|---|---|
| 当前时间 | rank 0 | 随每次匹配广播 |
| 计费长度、可复用长度 | rank 0 | 随每次匹配广播 |
| 租约表内容 | rank 0 的时间戳 + 各 rank 相同的输入 | 各 rank 用相同的 `now` 执行相同的操作 |
| 淘汰顺序、写 L3 的节点、清除的节点 | 各 rank 本地计算 | 输入一致，结果一致 |
| 写入预算计数 | 各 rank 本地计算 | 按逻辑 token 数扣减，与 I/O 完成事件无关 |

v0.4 的限制继续适用：`pp_size` 必须为 1；不支持与显式引擎会话、PD 模式的状态复用组合；与投机解码的组合未验收。

### 4.10 需要新增的指标

| 指标 | 用途 |
|---|---|
| 新 token 流入 L2 的速率（R） | 所有容量计算的输入 |
| 每 token 在 L3 上的实际字节数（b） | 同上 |
| 1h 档流量占比（f） | 同上 |
| L2 淘汰时条目的空闲时长（直方图） | 直接测量周转时间 |
| 命中时条目的空闲时长（直方图），分计费命中和过期复用 | 评估 `T_keep` 取多长才划算 |
| 物理命中 token 数 / 计费命中 token 数 | 之差是过期复用省下的计算量；后者用于对账 |
| 缓存写入 token 数，按 5m / 1h | 对账 |
| 有效期内被容量淘汰的 token 数，按档位 | TTL 承诺的违约率 |
| L3 写入 token 数和字节数；因来不及或预算用完而丢弃的 token 数 | 调队尾区域和预算 |
| 当日写入预算余量；磁盘磨损百分比 | 磁盘寿命 |
| 因超留存上限被清除的 token 数，按层 | 留存机制是否在起作用 |
| 租约表行数；匹配时查租约的耗时 | TTL 机制本身的开销 |

### 4.11 分阶段

| 阶段 | 内容 | 是否改变行为 |
|---|---|---|
| P0 | 加指标，测出 R、b、f；确认磁盘耐久等级；据 2.7 判断是否需要 L3 | 否 |
| P1 | 内存租约表 + 三个长度 + 用量字段（含默认 5m、档位锁定）。不接 L3 | 是：对外出现 TTL 语义 |
| P2 | 留存上限的三道措施 + 新的淘汰策略 | 是：影响淘汰顺序和数据留存 |
| P3 | 按 TTL 门控、带写入预算的 L3 后台写入 | 是：1h 档开始有容量保障 |

P1 只靠 L1 + L2 就能提供完整的语义。P3 是否必做取决于 P0 的结果：R 低于 C2 / 3600 的部署可以不做；高于它的部署，P3 之前 1h 档的实际保持时间约等于 L2 周转时间。

### 4.12 验证清单

- **语义**：沿用 v0.4 的用例（含 360 秒 / 600 秒到期案例）；新增"过期后物理复用但字段为未命中""默认 5m""档位锁定与继承""过期后换档"。
- **字段**：三种 API 的读取、写入、普通输入之和等于总输入；过期复用时读取字段为 0；分来源明细不暴露物理命中。
- **一致性**：多 rank 下在到期边界和留存边界附近反复请求，各 rank 的树状态、淘汰结果一致。
- **留存**：空闲超过 `T_keep` 的数据匹配不到；一个清除周期后内存和磁盘上都不存在。
- **开销**：开启前后对比 TTFT 和吞吐。
- **容量**：按 4.8 的条件表逐档压测，核对违约率、L3 写入量和预算行为。
- **投机解码**：在投机解码开启的条件下重跑语义用例。
- **与 Kimi 对齐**：第 5 节的全部条目。

## 5. 验收标准：与 Kimi 对齐

依据：[Kimi 上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)（含"两档 TTL 怎么选""如何设置缓存 TTL""查看缓存读写用量""常见问题"各节）。本节与引擎无关，SGLang 和 vLLM 的实现都按它验收。

### 5.1 总原则：可观测等价

定义一个**参考模型**：只按 Kimi 公开语义运行的纯逻辑模拟器。它只有租约表，没有物理层——假设数据在租约有效期内一定在，过期后一定不在。输入是带时间戳的请求序列，输出是每个请求的缓存相关字段。

验收通过的定义：**对任意请求序列，本系统返回的缓存相关字段与参考模型逐请求完全一致。**

本系统内部的过期复用、分层、淘汰、写 L3 等行为，都不得在字段上留下痕迹。允许的偏差只有一种：有效期内被容量淘汰导致的未命中（参考模型说命中、本系统说写入），它对应 4.10 的违约率指标；验收在容量充足的条件下进行，要求这类偏差为零。

### 5.2 语义对齐清单

| # | Kimi 行为（文档原意） | 本方案对应 | 验收用例 |
|---|---|---|---|
| S1 | 缓存按请求前缀匹配，前缀任一处变化后，其后内容不再复用 | 链式页哈希（4.2） | 改动前缀中间一个 token，之后部分全部计为写入 |
| S2 | 缓存按块存储，不足一整块的部分不写入，计为未命中（Input） | 不足一页的尾部计普通输入（4.5） | 输入长度不是页大小整数倍时，尾部既不在读取也不在写入里 |
| S3 | 不传 `prompt_cache_options` 时默认 5m，自动写入并产生写入费 | 决定 1（4.1） | 不传选项的请求，写入字段非零且记在 5m |
| S4 | `mode` 只支持 `implicit`，`ttl` 只支持 `5m` / `1h` | 4.1 | 其他值返回 400 |
| S5 | 命中后免费续期，有效期从命中时刻按原 TTL 重算 | 4.4 | 1h 写入后 30 分钟命中，再过 50 分钟仍命中；再过 61 分钟未命中 |
| S6 | TTL 首次写入时锁定；有效期内命中按原 TTL 续期；新增部分按锁定的 TTL 写入；完全过期后才能按新 TTL 重写 | 决定 2（2.2 第 5 条、4.4） | 1h 请求命中有效的 5m 前缀：续期按 5m，新增页写入记在 5m；该前缀过期后再发 1h 请求，写入记在 1h |
| S7 | 无活动超过所选 TTL 后自动过期；"5m 档至少 5 分钟无活动后过期" | `now >= expires` 判定（2.2 第 2 条）；留存上限只影响内部 | 空闲 TTL − 1 秒命中，空闲 TTL + 1 秒未命中 |
| S8 | 按组织隔离，组织内共享 | 隔离域由 `cache_salt` / extra key 决定（2.6） | 两个隔离域发相同前缀，互不命中 |
| S9 | 不支持手动清除 | 不提供清除接口 | 无接口可调 |
| S10 | 命中部分不再收写入费，只按命中计费 | 4.5 | 全部命中的请求，写入字段为 0 |
| S11 | "5m 与 1h 两个缓存不互通" | 与 S6 的锁定规则有出入，本方案以 S6 为准 | 用 5.4 的官方端点对照确认实际行为，再定用例 |

| # | API | Kimi 字段 | 验收要求 |
|---|---|---|---|
| F1 | Chat Completions | `usage.prompt_tokens`、`usage.prompt_tokens_details.cached_tokens`、`usage.prompt_tokens_details.cache_write_tokens` | 读取、写入、未缓存三者互斥，之和等于 `prompt_tokens` |

### 5.4 内部复用不可感知

过期复用（2.1 表第二行）必须和"数据不存在、重新计算"（第三行）在字段上完全相同：

| 项目 | 要求 |
|---|---|
| 读取字段 | 复用部分计 0 |
| 写入字段 | 复用部分按 4.4 得到的档位计入，数值与重新计算时相同 |
| 后续行为 | 复用后建立的租约，其续期、锁定、过期行为与新写入完全一致 |
| 分来源明细 | 不区分"物理复用"和"重算"，见 F7 |
| 响应头 | 同写入字段 |

唯一可感知的差异是首 token 延迟会比真正重算短。它不在字段验收范围内，本方案不为掩盖它人为增加延迟。

### 5.5 验收方法

1. **参考模型**：按 5.2 的规则实现一个纯函数模拟器，作为测试预言。它不依赖引擎，可以单独做单元测试。
2. **差分测试**：同一请求序列在本系统和参考模型上各跑一遍，逐请求比对 5.3 的全部字段。用例覆盖 5.2 的每一行，以及 5.4 的"过期后数据仍在"和"过期后数据已被淘汰"两种情形，两者的字段必须相同。
3. **官方端点对照**：同一序列打到 Kimi 官方端点，记录返回字段，用来校准参考模型，尤其是 S11 这类文档表述有出入的条款。v0.4 的文档明确说没做过这一项，本版必须做。
4. **可注入时钟**：rank 0 是时钟权威（2.5），测试时通过它注入时间，不真等 1 小时。
5. **三种 API 各跑一遍**：Chat Completions、Responses、Messages，流式与非流式都覆盖。
