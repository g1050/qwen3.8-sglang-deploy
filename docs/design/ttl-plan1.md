# Prompt Cache TTL 支持方案（plan1）

- 日期：2026-11-13（第五稿：按 v0.2.0 的实现、官方端点对照和压测结论修订）
- 范围：单机、单实例（多卡 TP）的推理服务，支持 5m / 1h 两档缓存 TTL
- 状态：SGLang 部分已在 Qwen3.8-27B-FP8 / SGLang 0.5.20 / 8×RTX 5090 上实现并验收，随 qwen3.8-deploy v0.2.0 发布；vLLM 部分待验证
- 前置：kimi3.1-deploy 的 v0.4 TTL 实现（`compat/cache_ttl.py`、`compat/cache_hooks.py`），本方案是在它之上的第二版
- 配套：开发文档 [../ttl-v020.md](../ttl-v020.md)；第四稿原文见本文件的上一个 Git 版本

第五稿相对第四稿的实质变化（详见第 9 节）：

1. 计费只看租约，不再与物理命中长度取较小值（2.2、4.3、5.1）。
2. 时钟取请求到达时间戳，不做每次匹配的跨 rank 广播（2.5、4.9）。
3. 租约和计费粒度是 256 token 的块，与引擎页大小解耦（4.2）。
4. L3 只在"确实写过盘"时才查盘，队尾写入按淘汰量摊销（2.4、4.7）。
5. S11 已用官方端点确认：以档位锁定为准（5.2）。

本文是总纲，不绑定具体模型和机器。所有容量相关的内容都用参数和公式表达，落地到某个部署时代入该部署的实测值。附录 A 给了两个算例，仅作示意。

文中结论的来源分四类：**已核实**（读过源码）、**已实测**（v0.2.0 上测量或官方端点对照）、**推断**（由已核实的事实推出，未直接测量）、**待确认**。

## 1. 目标

对外提供和 Kimi / Anthropic 官方一致的缓存 TTL 语义：

1. 有效期内命中，按缓存命中计费。
2. 过期后不算命中，按未命中（缓存写入）计费，返回字段与未命中一致。
3. 命中即续约，有效期从命中时刻重新计算。
4. 支持 5m 和 1h 两档；不传时默认 5m。
5. **验收目标**：与 Kimi 的缓存机制一致，语义对齐、字段对齐，依据是 [Kimi 上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)。内部"过期但数据仍在则直接复用"的行为保留，但客户不能通过任何返回字段感知到差异。验收标准见第 5 节。

内部目标：

- 尽量少做重复的 prefill 计算。
- TTL 机制本身不拖慢推理。
- 缓存数据的物理留存时间有明确上限。

### 已定的四项决定

| # | 问题 | 决定 |
|---|---|---|
| 1 | 不传 TTL 时 | 对齐 Kimi 官方，默认 5m |
| 2 | 不同档位命中同一份有效缓存 | 首次写入锁定档位 |
| 3 | 过期后内部复用的计费 | 按未命中计费，返回字段符合未命中 |
| 4 | 物理留存上限 | 结合吞吐和磁盘空间设计，见 4.8 |

## 2. 整体策略与思想

### 2.1 核心思想：物理状态和计费状态分离

一份 KV 缓存有两个互相独立的状态：

| 状态 | 含义 | 由谁决定 |
|---|---|---|
| 物理状态 | KV 数据还在不在（L1 / L2 / L3） | 容量、淘汰策略、留存上限 |
| 计费状态 | 对用户算不算命中 | TTL 租约 |

以条目"最后一次被使用"的时刻为起点，按空闲时长分成三段：

| 空闲时长 | 物理 | 计算 | 对用户 |
|---|---|---|---|
| 小于 TTL | 可用 | 跳过 prefill | 命中 |
| TTL 到留存上限之间 | 可用（如果还没被容量淘汰） | 跳过 prefill | 未命中，按写入计费，并重新建立租约 |
| 超过留存上限 | 不可用，等待清除 | 重新计算 | 未命中，按写入计费 |

第二段是本方案相对 v0.4 的主要变化：**过期不等于删除**。过期数据只要还在、且没超过留存上限，推理系统就直接复用，只是对用户报告未命中。输出不受影响，因为复用 KV 和重算在数值上等价。

### 2.2 语义规则

1. **有效期内命中**：从请求开头起、连续且租约有效的那一段前缀，算计费命中。计费只看租约，与数据此刻是否物理存在无关（原因见 4.3）。
2. **过期不命中**：到期判定用 `now >= expires`。过期部分按写入计费。
3. **命中续约**：只续约本次请求实际采用的前缀。只是探测、还在排队的请求不续约；兄弟分支和没用到的长尾不续约。（沿用 v0.4）
4. **默认档位**：请求不带 TTL 时按 5m 处理。所有请求都走 TTL 路径，不再有"不过期"的原生路径。
5. **首次写入锁定档位**：
   - 租约有效期内档位不变，命中按原档位续约，与本次请求传的档位无关。
   - 在一段有效前缀后面新增的页，继承该前缀的档位。（Kimi 文档："新增部分也按锁定的 TTL 继续写入"）
   - 只有前一页已过期或不存在时，新页才采用本次请求的档位。
   - 效果：请求传 1h、但命中的是一段有效的 5m 前缀时，整条链仍是 5m，写入量记在 5m 字段里。要换档只能等它完全过期。
6. **活动请求不受影响**：已经采用缓存的请求继续用自己的状态，不会中途被清空。（沿用 v0.4）
7. **TTL 对用户是硬承诺，对容量是软承诺**：容量压力下数据可能在有效期内被淘汰，之后正常重算，但仍按命中计费，重算成本由服务方承担，并计入内部指标（4.10 的 `unbacked_read`）。
8. **缓存块为 256 token**（已实测，与 Kimi 官方一致）：只有完整的块进入租约表，不足一块的尾部计普通输入。

### 2.3 一份有效期状态，三级共用

有效期是条目的逻辑属性，不属于某一层。L1、L2、L3 共用一张**租约表**：键是页的链式哈希，值是"最后使用时间"和"档位"。数据在层间移动时租约不变。

它不挂在前缀树节点上，原因是（已核实）SGLang 在 L2 淘汰时会把节点从树里删除，而且树不保存 L3 的元数据。

由"最后使用时间"可以同时算出两件事：

- 租约是否有效：`now < 最后使用时间 + TTL`
- 是否允许物理复用：`now < 最后使用时间 + 留存上限`

租约表里查不到的页，一律视为超过留存上限、不可复用。因此记录可以提前清理（效果只是少复用一次），进程重启后表为空也是安全的。

### 2.4 分层策略

| 层 | 介质 | 策略 |
|---|---|---|
| L1 | GPU 显存 | 原生 LRU，不变 |
| L2 | 主机内存 | 超过留存上限的最先淘汰，其次是租约已过期的，其余按 LRU |
| L3 | 本地 NVMe | 只接收"1h 档、租约有效"的条目，后台提前写入，受每日写入预算限制 |

**5m 档不写 L3**。条目被挤到 L2 队尾时，如果是 5m 档或租约已过期就直接丢。

**写 L3 的时机**：在 L2 淘汰之前写队尾，不是每次淘汰都写。

- 触发信号：L2 的淘汰需求。每累计一个窗口的一半（v0.2.0 为 3.2 万 token）扫描一次 L2 的 LRU 队尾，覆盖一个窗口（6.5 万 token）。**不能用占用率做触发**，缓存稳态下永远是满的。也**不能每次淘汰都扫描**：扫描要对全部主机叶子排序，而且写得越多、引擎的写盘线程占用调度器进程越久（已实测，见 9.2）。
- 写入条件：1h 档；租约剩余时间大于下限（5 分钟）；未写过盘；写入预算未用完。
- 预算用完时：直接丢弃并计数。
- 引擎原生的"每次主机备份都写 L3"必须关闭，否则 5m 档和过期数据也会落盘。

**读 L3 的时机**：只在"内存匹配点之后紧接的块确实写进过 L3、且仍在留存期内"时才查盘，查不到不重试。绝大多数请求完全由内存满足；无条件查盘会把请求卡在调度之前（已实测，见 9.2）。

写入量的上限是 L2 的淘汰速率和写入预算，不是占用率，所以不会"一直写"。

### 2.5 时钟与一致性

多卡 TP 下每个 rank 是独立进程，各有一棵前缀树，必须做出完全一致的决策。

规则：**唯一的时钟是请求到达 HTTP 进程时打上的时间戳**，各 rank 的本地时钟不参与任何决定。

（已核实）SGLang 的 rank 0 已经把同一份请求列表广播给所有 rank。时间戳和 TTL 秒数随请求一起到达每个 rank，各 rank 取"已见时间戳的最大值"作为当前时间，用相同的输入维护各自的租约表副本，结果逐条一致。因此不需要 v0.4 那样在每次匹配时再做一次跨 rank 广播。

代价：没有新请求时时钟不前进。它只影响后台清理的时机，不影响正确性，因为所有判定都发生在处理请求时。

（已核实）前缀树节点自带的 `last_access_time` 是逻辑计数器（每次加 1.0），不是真实时间，不能用来判断过期，必须另记广播来的时间戳。

时间水位单调不减，系统时钟回拨不会让已过期的租约复活。（沿用 v0.4）测试时通过请求头注入时间戳，不必真等一小时（5.5）。

### 2.6 隔离与对外可见性

- **隔离**：过期数据的内部复用限定在同一个隔离域内（`cache_salt` / extra key）。（已核实）SGLang 原生的页哈希以 `extra_key` 和 `cache_salt` 为种子，天然按隔离域区分。
- **对外可见**：所有返回给用户的字段只反映租约（见 4.5）。过期复用时延迟比真正的未命中短，有效期内数据被淘汰时延迟比真正的命中长，这两点无法隐藏。
- **留存**：对外措辞为"至少保留 TTL 时长"；内部以留存上限为硬边界，超过后既不复用也不保留（见 4.8）。

### 2.7 容量模型

TTL 能不能守住、要不要 L3、L3 该多大，都由下面几个参数决定。它们因部署而异，需要实测。

| 符号 | 含义 | 来源 |
|---|---|---|
| C2 | L2 容量（token） | 配置 |
| S3 | L3 配额（字节） | 配置 |
| b | 每 token 的 KV 字节数（所有 rank 合计） | 实测 |
| R | 新 token 流入 L2 的速率（token/秒） | 实测 |
| f | 1h 档流量占比 | 实测 |
| V | L3 所在磁盘的容量 | 硬件 |
| D | 磁盘耐久等级（每日全盘写入次数） | 厂商规格 |
| T_keep | 物理留存上限 | 本方案设定 |

**L2 周转时间**：L2 满的时候，淘汰速率约等于流入速率，所以

```
T2 = C2 / R
```

条目被挤到 L2 队尾时，大约已经空闲了 T2。这是上限估算：被反复命中的老条目也占空间，实际会更短。

由此得到两个流入速率门槛：

| 门槛 | 含义 |
|---|---|
| R < C2 / 3600 | L2 自己能撑住 1 小时。被淘汰的条目都已过期，L3 基本不写 |
| C2 / 3600 < R < C2 / 300 | L2 撑不住 1 小时，1h 档依赖 L3 |
| R > C2 / 300 | L2 连 5 分钟都撑不住，5m 档开始违约 |

**L3 的三个约束**。设 L3 的写入速率为 W3（token/秒），最坏情况 W3 = f · R：

| 约束 | 条件 |
|---|---|
| 空间 | W3 · b · T_keep ≤ S3 |
| 寿命 | W3 · b · 86400 ≤ D · V · L3 份额 |
| 带宽 | W3 · b 远小于磁盘的持续顺序写速度 |

三者中哪个最紧取决于 b：b 越大，寿命约束越先到。寿命约束给出 L3 写入速率的上限：

```
W3_max = D · V · L3 份额 / (86400 · b)
```

**1h 档有容量保障的条件**：`f · R ≤ W3_max`。不满足时，预算用完后的 1h 条目会被丢弃，表现为违约率上升，解决办法是加盘、加内存或换耐久等级更高的盘。

要不要接 L3 的判断方法：先测 R，和 C2 / 3600 比较。附录 A 的两个算例显示，不同部署下结论可以完全相反。

## 3. 与现有 v0.4 实现的差异

v0.4 的做法（已核实）：把 TTL 秒数编码进 `cache_salt`；用 SQLite 记录每页的到期时间；匹配前按租约截短查找 key，过期部分不允许从任何一层命中。

| 方面 | v0.4 | 本方案 | 原因 |
|---|---|---|---|
| 过期后的物理数据 | 禁止命中，重新计算 | 留存上限内内部复用，只在计费上算未命中 | 减少重复 prefill |
| TTL 与隔离域 | TTL 编进 `cache_salt`，不同档位各占一个命名空间 | TTL 是租约表里的状态 | 同一内容不再按档位各存一份；实现档位锁定 |
| 不传 TTL | 走原生路径，不过期 | 默认 5m | 决定 1 |
| 匹配时截短 key | 截到租约有效长度 | 截到留存上限允许的长度 | 物理复用范围变大，但仍有边界 |
| 用量统计 | 原生统计，适配器不改 | 物理命中和计费命中分开，对外只报计费 | 决定 3 |
| 租约存储 | SQLite，WAL + `synchronous=FULL`，仅 rank 0 | 内存表，各 rank 一份副本 | 见下方说明 |
| 跨 rank 同步 | 每次匹配广播查找长度 | 不广播，时间戳随请求到达 | 少一次同步点 |
| 计费与物理 | 同一个长度 | 计费只看租约 | 物理恢复点是内部细节（4.3） |
| 持久化 | 重启后保留有效期 | 默认不持久化 | 表为空是安全的 |
| 淘汰 | 原生 LRU | 超上限优先，过期其次，其余 LRU | 让无用数据先腾位置 |
| 写 L3 | 原生策略，不看 TTL | 只写 1h 档有效的，后台提前写，有写入预算 | 控制写入量和磁盘寿命 |
| 物理留存 | 不限，交给容量回收 | 有硬上限和清除机制 | 决定 4 |

**保留 v0.4 的部分**：按链式页哈希记租约；rank 0 权威加广播；只续约实际采用的前缀；探测不续约；活动请求保留自己的状态；时间水位单调；`prompt_cache_options` 的解析和校验；匹配、预取两处的截短 hook（截短长度的含义变了）。

**关于 SQLite（推断，未实测）**：v0.4 每次查找都在事务里更新时间水位，而连接设置了 `synchronous=FULL`，所以每次缓存查找都会触发一次落盘同步。改成内存表可以把这一项从请求热路径上拿掉。

## 4. SGLang 实现细节

源码依据：SGLang 0.5.20。下文路径相对于 `python/sglang/srt/`。落地到其他版本时，涉及具体函数的地方需要重新对照。

### 4.1 请求入口

沿用 v0.4 的解析和校验（正整数加 `s/m/h/d`，非法值返回 400），改动：

- TTL 不再是隔离域的一部分。实现上仍借用 `cache_salt` 字段把 `(TTL 秒数, 到达时间戳, 原始 salt)` 带到每个 rank，在调度器创建请求对象时立刻还原成原始 salt，缓存键里不含 TTL。这样不必改动引擎的传输结构。
- 不带 TTL 的请求填默认值 5m。
- 对外只开放 `5m` 和 `1h` 两个值（已实测，官方对其他值返回 400）。
- Anthropic 兼容接口的顶层 `cache_control: {"type": "ephemeral", "ttl": "1h"}` 映射到同一个字段；消息体内的同名标记忽略。

### 4.2 租约表

```
键：256 token 块的链式哈希，以 (cache_salt, extra_key) 为种子
值：(last_used, expires, ttl_seconds)
```

- 不直接用引擎原生的页哈希。原因：计费块固定为 256 token，而引擎页大小是部署参数（本部署为 64），两者必须解耦；块大小要求是引擎页大小的整数倍。
- 每个请求的各块键只算一次并缓存在请求对象上。
- 只覆盖完整的块，不足一块的尾部不进租约表，计为普通输入。
- 内存字典，每个 rank 一份，由相同的请求序列驱动，保持逐条一致。
- 记录保留到 `last_used + T_keep`，之后清理（每 60 秒扫一次）。（已实测）8 并发一小时约 1.3 万行。
- 生成的输出 token 也会进入前缀树。它们在租约表里登记为"可复用、未计费"（`expires = 0`），下一轮对话把它们当作 prompt 发回时按写入计费，但不需要重算。

### 4.3 匹配：两个长度

1. 对请求各块查租约表，得到：
   - **计费长度**：从头开始连续"租约有效"的块数 × 块大小
   - **可复用长度**：从头开始连续"未超留存上限"的块数 × 块大小（不小于计费长度）
2. 把查找 key 截到可复用长度，再调原生 `match_prefix`，得到**物理长度**。
3. 计费命中 = 计费长度。物理长度只进内部指标。

第四稿规定"计费命中 = min(计费长度, 物理长度)"，实现后放弃（已实测）。带状态层的模型（本部署含 Mamba 状态）只能从状态检查点恢复，物理长度会落在检查点上而不是租约边界上。例如改动前缀中部时，租约有效 7424 token，物理只能复用 4096。取较小值会把这个内部细节暴露在计费字段里，与参考模型不一致。同理，并发请求共享前缀时，后到的请求可能在数据算完之前被调度。

截短的做法和 v0.4 相同（`match_prefix`、`_compute_max_prefix_len`、`_prefetch_kvcache` 三处 hook），截短长度是"可复用"。L3 预取同样受这个长度限制，保证超过留存上限的旧文件读不回来。

命中会续约整条已用路径，祖先的最后使用时间不早于后代，所以两个长度都天然是连续前缀。

### 4.4 续约与写入

时机：请求第一次进入 prefill 批次时（`ScheduleBatch.prepare_for_extend` 更新缓存使用计数之后），对整个 prompt 一次完成。只是探测、还在排队的请求不触发。v0.4 把"续约"和"新页登记"分在两个时机做；本方案的计费不依赖物理写入是否成功，所以合并。

对 prompt 的每一块，按顺序处理：

| 块的状态 | 动作 | 档位 | 计费 |
|---|---|---|---|
| 在计费长度以内 | `last_used = now`，`expires = now + 原档位` | 保持原档位 | 命中 |
| 其余 | 新建记录，`last_used = now` | 计费长度不为 0 时继承其最后一块的档位，否则用本次请求的档位 | 写入，记到所得档位 |

一个请求的全部写入属于同一个档位。请求结束、输出并入前缀树后，输出块按 4.2 登记为"可复用、未计费"。

同时给请求实际用到的树路径打上 `(last_used, expires, 档位)` 标记，供淘汰排序和 L3 写入判断使用（4.6、4.7）。

`now` 一律用 2.5 的请求时钟。

### 4.5 用量上报：字段必须符合未命中

每个请求产出：

- 缓存读取 = 计费命中长度
- 缓存写入（5m）、缓存写入（1h）= 按 4.4 得到的各档位写入页数 × 页大小
- 普通输入 = 不足一页的尾部

**原则：凡是返回给用户的字段，一律用计费口径；物理口径只进内部指标。** 过期复用的部分在读取字段里是 0，在写入字段里按所得档位计数。

对外字段（已实测，与 Kimi 官方端点一致）：

| API | 缓存读取 | 缓存写入 |
|---|---|---|
| Chat Completions | `usage.prompt_tokens_details.cached_tokens`，命中时另有顶层 `usage.cached_tokens`；未命中时两者都不出现 | `usage.prompt_tokens_details.cache_write_tokens` |
| Responses | `usage.input_tokens_details.cached_tokens` | `usage.input_tokens_details.cache_write_tokens` |
| Messages | `usage.cache_read_input_tokens` | `usage.cache_creation_input_tokens`，以及 `usage.cache_creation.ephemeral_5m_input_tokens` / `ephemeral_1h_input_tokens` |

- Chat Completions 和 Responses：读取、写入、未缓存三者互斥，之和等于总输入。
- Messages：`usage.input_tokens` 不含读取和写入部分。
- 三种 API 都带响应头 `Msh-Usage-Cache-Write-Tokens-5m` 和 `Msh-Usage-Cache-Write-Tokens-1h`（官方三种 API 都返回）。流式响应的头要等请求被调度、账单确定后才能发出，在此之前的事件先缓冲。
- 流式请求在最后一个 chunk 的 usage 里给出完整明细。

实现路径（v0.2.0）：不改引擎文件。调度器把账单 `[读取, 写入5m, 写入1h, 总输入]` 放进原有的 `cached_tokens_details` 字段带到 HTTP 进程；HTTP 进程的中间件取走这个字段、改写 JSON 和 SSE 里的 usage、加响应头。分来源明细（device / host / storage）因此不再返回给用户。

n > 1 或批量请求共享同一个 prompt，账单取第一个 choice 的。

### 4.6 淘汰

（已核实）树核心持有一个可插拔的淘汰策略对象（`unified_cache/unified_tree_core.py` 里的 `self.eviction_strategy`，由 `get_eviction_strategy` 创建），每个策略只返回一个排序键，值小的先淘汰。

新增一个策略，排序键为 `(等级, last_access_time)`：

| 等级 | 条件 |
|---|---|
| 0，最先淘汰 | 超过留存上限（租约表里查不到） |
| 1 | 租约已过期，仍在留存上限内 |
| 2 | 租约有效 |

等级判断读本 rank 的租约表副本和广播来的 `now`，各 rank 结果一致。

等级读节点上的标记（4.4）和请求时钟。没有标记的节点第一次被淘汰排序看到时，按默认 5m 起算。

（已核实）KV 的 L2 淘汰（`components/full.py` 的 `drive_host_eviction`）用的是同一个策略对象，所以 L1 和 L2 的 KV 共用这个排序。带状态层的模型，其状态池（Mamba）走自己的 LRU 链表，不经过这个策略对象，v0.2.0 没有改它。

### 4.7 L3 写入

（已核实）现状：

- 写策略是全局开关 `--hicache-write-policy`（`write_through`、`write_through_selective`、`write_back`），不区分请求。
- `write_backup_storage(node_id)` 可以对任意一个在 L2 的节点发起写 L3；写入期间给节点加主机侧的锁，写完才释放。
- 自带多种 L3 后端，包括本地 `file`。单机场景用本地文件后端即可，不需要分布式存储。

v0.2.0 的做法：

1. 拦截原生的写 L3 入口，只放行本方案发起的写入。
2. 在 L2 淘汰入口按 2.4 的规则扫描队尾并写入，从写入预算（令牌桶）里扣除。写入期间节点被锁，本轮淘汰会跳过它。
3. 写过盘的块记入一个集合（键为租约块键），随租约表一起清理。
4. 请求到达时，只有"内存匹配点之后紧接的块在这个集合里、且未超留存上限"才发起 L3 预取；预取重试上限设为 1。
5. 从 L3 读回 L2 之后，不删除 L3 上的副本。

注意点：

- 写入期间节点不能淘汰，队尾区域要留足提前量。
- 触发条件只读逻辑状态（淘汰需求累计量、节点标记、预算计数），不读"某次写入是否完成"这类事件，保证各 rank 一致。预算按请求时钟补充。
- KV 按 rank 切分时每个 rank 各写自己的一份，合起来才是完整的一页，取回时缺一不可。
- L3 目录按镜像摘要、启动参数分命名空间（沿用 v0.4），不同配置不混读。
- 文件后端的存在性缓存要打开并设为不过期，否则每次查盘都扫描目录。

### 4.8 物理留存上限

#### 定义

留存上限 `T_keep`：一页 KV 自最后一次被使用起，最多允许存在和被复用的时长。三层共用一个值。

它是上限而不是保证。实际留存时间还受容量限制，是下面几项中最短的一个：

| 层 | 实际留存时间 |
|---|---|
| 内存（L1 + L2） | min(T_keep, C2 / R) |
| 磁盘（L3） | min(T_keep, S3 / (W3 · b)) |

#### 取值规则

| 参数 | 规则 | 默认 |
|---|---|---|
| `T_keep` | 最长 TTL + 过期复用窗口 | 2 小时（1 小时 + 1 小时） |
| 每日写入预算 | D · V · L3 份额 | 耐久等级未知时按 D = 1 |
| L3 写入速率上限 | W3_max = 每日写入预算 / (86400 · b) | 由上一项导出 |
| L3 配额 S3 | W3_max · b · T_keep，即 每日写入预算 × T_keep / 24 小时 | 由上两项导出 |
| 磁盘最低空闲 | 按盘上其他用途留余量 | 部署时定 |
| 预算形式 | 令牌桶，按小时均摊，允许短时突发 | — |

说明：

- **L3 配额由寿命预算和 `T_keep` 共同决定。** 在寿命允许的写入速率下，`T_keep` 时间内最多能写这么多数据；超过上限的会被清除。配额比这个数更大没有意义。
- **`T_keep` 的过期复用窗口取多长**，取决于"用户过期后多久回来"的分布。默认 1 小时，上线后看"命中时条目已空闲多久"的直方图调整（见 4.10）。窗口越长，省的计算越多，占的 L3 配额也越多。
- **L3 与其他数据共用一块盘时**，寿命和空间都要按份额分，不能按整盘算。

#### 各种负载下谁是瓶颈

| 条件 | 结果 |
|---|---|
| R < C2 / 3600 | L2 够用，L3 基本不写，留存由 `T_keep` 决定 |
| R > C2 / 3600 且 f · R ≤ W3_max | 1h 档靠 L3 保住，写入在寿命预算内 |
| f · R > W3_max | 预算用完后 1h 档部分违约；需要加盘、加内存或换更耐写的盘 |
| R > C2 / 300 | 5m 档也开始违约 |

#### 执行机制

留存上限靠三道措施保证，第一道保证"不再使用"，后两道保证"不再存在"：

1. **匹配时拒绝**：查找 key 截到可复用长度（4.3），超过上限的数据即使还在也不会被用到。这一条是即时生效的硬保证。
2. **淘汰优先**：超过上限的节点在淘汰排序里排最前（4.6）。
3. **定时清除**：每 5 分钟处理一次：
   - L3：删除写入时间超过 `T_keep` 的对象文件（按文件修改时间，从最老的开始）。
   - L1 / L2：v0.2.0 **没有实现**主动释放。等级 0 的节点只保证匹配不到、淘汰时排最前。

因此 L3 上数据的最长存在时间是 `T_keep` 加一个清除周期；L1 / L2 里超过上限的数据会留到下一次容量淘汰。若留存上限是合规要求而不只是容量手段，需要补上 L1 / L2 的主动释放（遗留项，见第 7 节）。

#### 进程重启

重启后租约表为空，L1 和 L2 也是空的，L3 上的残留文件全部视为不可复用，由定时清除删掉。行为简单且严格。

可选增强：定期把租约表异步快照到磁盘（不在请求路径上同步落盘），启动时加载并丢弃已超上限的记录。这样重启后 L3 里仍有效的 1h 缓存可以继续用。是否需要，看重启频率。

### 4.9 多 rank 一致性清单

| 决策 | 权威 | 传播方式 |
|---|---|---|
| 当前时间 | HTTP 进程的到达时间戳 | 随请求到达每个 rank |
| 计费长度、可复用长度 | 各 rank 本地计算 | 输入一致，结果一致 |
| 租约表内容 | 各 rank 相同的请求序列 | 各 rank 执行相同的操作 |
| 淘汰顺序、写 L3 的节点、清除的节点 | 各 rank 本地计算 | 输入一致，结果一致 |
| 写入预算计数 | 各 rank 本地计算 | 按逻辑 token 数扣减，与 I/O 完成事件无关 |

v0.4 的限制继续适用：`pp_size` 必须为 1；不支持与显式引擎会话、PD 模式的状态复用组合。与投机解码的组合已验收（已实测：原生 MTP 开启时 51 项验收全部通过）。

|---|---|---|
| P0 | 加指标，测出 R、b、f；确认磁盘耐久等级；据 2.7 判断是否需要 L3 | 否 |

## 5. 验收标准：与 Kimi 对齐

依据：[Kimi 上下文缓存最佳实践](https://platform.kimi.com/docs/guide/context-caching)（含"两档 TTL 怎么选""如何设置缓存 TTL""查看缓存读写用量""常见问题"各节）。本节与引擎无关，SGLang 和 vLLM 的实现都按它验收。

### 5.1 总原则：可观测等价

定义一个**参考模型**：只按 Kimi 公开语义运行的纯逻辑模拟器。它只有租约表，没有物理层——假设数据在租约有效期内一定在，过期后一定不在。（v0.2.0：`compat/qwen_ttl/core.py` 的 `ReferenceModel`，已用官方端点校准。）输入是带时间戳的请求序列，输出是每个请求的缓存相关字段。

验收通过的定义：**对任意请求序列，本系统返回的缓存相关字段与参考模型逐请求完全一致。**

本系统内部的过期复用、分层、淘汰、写 L3 等行为，都不得在字段上留下痕迹。第四稿允许一种偏差（有效期内被容量淘汰时报未命中）；改为按租约计费（4.3）后这种偏差不存在，字段在任何容量条件下都与参考模型一致，容量淘汰只体现在内部指标 `unbacked_read` 上。

### 5.2 语义对齐清单

| # | Kimi 行为（文档原意） | 本方案对应 | 验收用例 |
|---|---|---|---|
| S1 | 缓存按请求前缀匹配，前缀任一处变化后，其后内容不再复用 | 链式页哈希（4.2） | 改动前缀中间一个 token，之后部分全部计为写入 |
| S2 | 缓存按块存储，不足一整块的部分不写入，计为未命中（Input） | 不足一页的尾部计普通输入（4.5） | 输入长度不是页大小整数倍时，尾部既不在读取也不在写入里 |
| S3 | 不传 `prompt_cache_options` 时默认 5m，自动写入并产生写入费 | 决定 1（4.1） | 不传选项的请求，写入字段非零且记在 5m |
| S4 | `mode` 只支持 `implicit`，`ttl` 只支持 `5m` / `1h` | 4.1 | 其他值返回 400 |
| S5 | 命中后免费续期，有效期从命中时刻按原 TTL 重算 | 4.4 | 1h 写入后 30 分钟命中，再过 50 分钟仍命中；再过 61 分钟未命中 |
| S6 | TTL 首次写入时锁定；有效期内命中按原 TTL 续期；新增部分按锁定的 TTL 写入；完全过期后才能按新 TTL 重写 | 决定 2（2.2 第 5 条、4.4） | 1h 请求命中有效的 5m 前缀：续期按 5m，新增页写入记在 5m；该前缀过期后再发 1h 请求，写入记在 1h |
| S7 | 无活动超过所选 TTL 后自动过期；"5m 档至少 5 分钟无活动后过期" | `now >= expires` 判定（2.2 第 2 条）；留存上限只影响内部 | 空闲 TTL − 1 秒命中，空闲 TTL + 1 秒未命中 |
| S8 | 按组织隔离，组织内共享 | 隔离域由 `cache_salt` / extra key 决定（2.6） | 两个隔离域发相同前缀，互不命中 |
| S9 | 不支持手动清除 | 不提供清除接口 | 无接口可调 |
| S10 | 命中部分不再收写入费，只按命中计费 | 4.5 | 全部命中的请求，写入字段为 0 |
| S11 | "5m 与 1h 两个缓存不互通" | （已实测）官方实际行为是 S6：5m 请求能命中有效的 1h 前缀，反之亦然，新增块按锁定的档位写入。文档这句话不成立，以 S6 为准 | 同 S6 |

| F5 | Chat Completions | 响应头 `Msh-Usage-Cache-Write-Tokens-5m`、`Msh-Usage-Cache-Write-Tokens-1h` | 与 usage 里的写入量一致；全部命中时为 0 |
| F6 | Chat Completions 流式 | `stream_options.include_usage=true` 时，最后一个 chunk 的 `usage` 含完整明细 | 流式与非流式同一请求的字段相同 |
| F7 | 全部 | 不得出现 Kimi 没有的、能反映物理状态的字段 | 分来源的命中明细（`cached_tokens_details`）要么关闭，要么只含计费口径 |

### 5.4 内部复用不可感知

过期复用（2.1 表第二行）必须和"数据不存在、重新计算"（第三行）在字段上完全相同：

| 项目 | 要求 |
|---|---|
| 读取字段 | 复用部分计 0 |
| 写入字段 | 复用部分按 4.4 得到的档位计入，数值与重新计算时相同 |
| 后续行为 | 复用后建立的租约，其续期、锁定、过期行为与新写入完全一致 |
| 分来源明细 | 不区分"物理复用"和"重算"，见 F7 |
| 响应头 | 同写入字段 |

唯一可感知的差异是首 token 延迟会比真正重算短。它不在字段验收范围内，本方案不为掩盖它人为增加延迟。

### 5.5 验收方法

1. **参考模型**：按 5.2 的规则实现一个纯函数模拟器，作为测试预言。它不依赖引擎，可以单独做单元测试。
2. **差分测试**：同一请求序列在本系统和参考模型上各跑一遍，逐请求比对 5.3 的全部字段。用例覆盖 5.2 的每一行，以及 5.4 的"过期后数据仍在"和"过期后数据已被淘汰"两种情形，两者的字段必须相同。
3. **官方端点对照**：同一序列打到 Kimi 官方端点，记录返回字段，用来校准参考模型。（v0.2.0 已做，结论见 9.1。）
4. **可注入时钟**：时钟是请求到达时间戳（2.5），测试时用请求头注入，不真等 1 小时。该入口只在验收时用环境变量打开。
5. **三种 API 各跑一遍**：Chat Completions、Responses、Messages，流式与非流式都覆盖。

## 7. 待确认与遗留事项

**遗留问题（v0.2.0 未解决）**

1. 一次调度器崩溃没有找到根因：L3 查盘还是无条件的那个版本，在 8 并发压测结束、客户端取消在途请求后，空闲检查报 `pool memory leak detected`（GPU KV 池 available + evictable 比 total 多 3264 token），8 个 rank 全部退出。改成精确查盘后的两轮压测和 L3 压力场景都没有复现，但不能证明已消除。
2. L1 / L2 没有主动释放超过留存上限的数据（4.8）。
3. 状态池（Mamba）的淘汰不受 TTL 排序影响（4.6）。
4. 显式传入 `prompt_cache_options` 的请求、以及 5m / 1h 混合流量没有做过压测。压测客户端不带缓存选项，1h 档是靠服务端开关把默认档位改成 1h 测的。
5. 1h 档的 TTFT P50 比 baseline 高 10%、P90 高 8%（平均值 +1.9%）。只跑了一次，无法区分波动和 L3 的影响。
6. 4.10 里未导出的指标。
7. 进程重启后租约表为空，L3 残留文件不可复用（4.8 的可选增强未做）。

**每个部署落地前需要实测或查明的**

8. 稳态下新 token 流入 L2 的速率 R、每 token 在 L3 上的字节数 b、1h 档占比 f。本部署的值见附录 A 算例 C。
9. L3 所在磁盘的耐久等级 D，以及它是否与其他数据共用。本部署未查明，按 D = 1、份额 0.5 保守取值。

**已解决**

- 四项决定已定，见第 1 节。
- L2 侧 KV 淘汰使用可插拔策略的排序键：已核实（4.6）。
- `file` 后端能按对象键做定时清除：已核实，通过其 LRU 回收器实现（4.8）。
- S11：已用官方端点确认（5.2）。
- 响应 usage 的组装位置、原生页哈希覆盖隔离域、节点访问时间是逻辑计数器：第四稿已核实。
- v0.4 的 SQLite 开销：未单独测量；v0.2.0 的内存表加全部记账在 8 并发一小时里合计占调度器约 3.2 秒（已实测）。

## 9. 实测结论与遇到的问题（v0.2.0）

环境：Qwen3.8-27B-FP8，SGLang 0.5.20，8×RTX 5090，TP8，上下文 262144；L1 约 79 万 token，L2 每 rank 47 GB（KV 池 142.5 万 token），L3 为 3.5 TB NVMe 的一半份额。压测为 InferenceX AgentX 8 并发、3600 秒、原生 MTP 加模拟接受率。原始记录在工程的 `results/` 下。

### 9.1 官方端点对照

`api.moonshot.cn`，`kimi-k3.1-pro`：

| 项目 | 结果 |
|---|---|
| 块粒度 | 256 token：385 → 256，1228 → 1024，4718 → 4608 |
| 默认档位 | 不传选项时写入记在 5m |
| 续期 | 5m：+270 秒命中，再 +270 秒仍命中，空闲 330 秒未命中。1h：+400 秒、+3400 秒、再 +3400 秒均命中 |
| 档位锁定 | 5m 请求命中有效的 1h 前缀，新增块记在 1h；1h 请求命中有效的 5m 前缀，新增块记在 5m；并且 5m 请求对 1h 租约的续期仍是 1h |
| 过期后换档 | 5m 链空闲 330 秒后发 1h 请求，全部按 1h 重写 |
| 非法 TTL | HTTP 400 |
| 字段 | 未命中时不返回 `cached_tokens`；命中时 Chat 另有顶层 `usage.cached_tokens`；三种 API 都有两个写入量响应头 |

### 9.2 性能

| 配置 | 输出吞吐 | 相对 baseline |
|---|---:|---:|
| baseline（L2 开，无 TTL、无 L3） | 85.20 tok/s | — |
| TTL，全部 5m，L3 开 | 84.66 tok/s | −0.6% |
| TTL，全部 1h，L3 开（第三次迭代） | 84.35 tok/s | −1.0% |

1h 档前两次迭代不合格，教训已写回 2.4 和 4.7：

| 迭代 | 相对 baseline | 原因 | 修正 |
|---|---:|---|---|
| 1 | −24% | 每个 1h 请求都查 L3，查不到重试 8 次，请求卡在调度之前（一小时内重试触顶 1064 次） | 只查确实写过盘的块，重试上限 1 |
| 2 | −9.4% | 每次 L2 淘汰都扫描并写入队尾，一小时写入 55 万 token；ITL 全程约 +6 ms | 队尾扫描按淘汰量摊销；预算突发量从 1 小时降到 10 分钟 |
| 3 | −1.0% | — | 采用 |

这两个问题在小规模功能测试里都看不出来，只有长时间压测才暴露。为此加了一个几分钟就能逼出 L3 写入和回读的压力场景（小 L2），用于回归。

### 9.3 缓存行为

| 观察 | 数值 |
|---|---|
| 5m 档：计费命中率 / 实际命中率 | 87.4% / 91.9%，差值来自过期内部复用（约 200 万 token 没有重算） |
| 1h 档：计费命中率 / 实际命中率 | 94.4% / 92.0%，差值是计费命中但需重算的 82 万 token |
| 实际命中的分层（baseline） | L1 34%，L2 60%，其余重算 |
| L3（1h 档一小时） | 写入 21.4 万 token、约 51 GB；查盘 11 次；读回约 1.1 万 token |
| 每 token 在 L3 上的字节数 b | 170–240 KB（8 个 rank 合计，含状态层） |
| 租约表 | 约 1.3 万行 |
| TTL 记账开销 | 一小时合计约 3.2 秒调度器时间 |

L3 在这个负载下几乎没被读到。压测只有一小时，活跃会话几分钟内就会再次命中自己的前缀（计费命中时的空闲时长 P95 约 10 分钟），被挤出 L2 的 1h 条目很少在测试时间内回来。L3 的价值要在"用户隔几十分钟再回来"的真实流量上才能评估。

### 9.4 功能验收

51 项用例，在正式配置（真实解码）和压测配置（MTP 加模拟接受率）下各跑一遍，全部通过：5.2 的 S1–S10、5.3 的 F1–F7、5.4 的过期复用不可感知、留存上限、以及 60 步随机序列与参考模型的逐请求差分。

## 附录 A：算例（仅示意，不属于方案本身）

算例 A、B 是第四稿时的估算（b 由内存占用反推）。算例 C 是 v0.2.0 所在部署的实测值，见本附录末尾。

| | 算例 A：内存大、KV 小 | 算例 B：内存小、KV 大 |
|---|---|---|
| L2 容量 C2 | 约 6090 万 token | 约 143 万 token |
| 每 token 的 KV，b | 约 39 KB | 约 260 KB |
| L2 撑住 1 小时的门槛，C2 / 3600 | 约 1.7 万 token/秒 | 约 400 token/秒 |
| L2 撑住 5 分钟的门槛，C2 / 300 | 约 20 万 token/秒 | 约 4750 token/秒 |
| 实测流入速率 R | 平均约 3600 token/秒 | 无稳态数据；预热峰值约 3900 token/秒 |
| L2 周转时间 | 上限约 4.7 小时 | R 为 1000 时约 24 分钟 |
| 是否需要 L3 | 当前负载下基本不需要 | 需要 |

在算例 B 上代入一块 3.84 TB 的 NVMe 作 L3：

| L3 写入速率 | 写盘带宽 | 每日写入量 | 每日全盘写入次数 |
|---|---|---|---|
| 100 token/秒 | 26 MB/秒 | 约 2.2 TB | 约 0.6 |
| 170 token/秒 | 44 MB/秒 | 约 3.8 TB | 约 1 |
| 500 token/秒 | 130 MB/秒 | 约 11 TB | 约 3 |

- 按 D = 1：W3_max 约 170 token/秒；`T_keep` 取 2 小时时，L3 配额约 320 GB 即够。
- 按 D = 3：W3_max 约 500 token/秒；L3 配额约 1 TB。
- 这个算例里寿命约束最紧，带宽和空间都远没到上限。

在算例 A 上，同样的写入速率换算成字节只有约七分之一，寿命约束宽松得多，而且当前负载下根本不需要写。

### 算例 C：v0.2.0 所在部署（实测）

| 参数 | 值 |
|---|---|
| L2 容量 C2 | 142.5 万 token（每 rank 47 GB，其中 KV 池 24.8 GB） |
| 每 token 的 KV，b | 内存约 139 KB；L3 上 170–240 KB |
| 流入速率 R（8 并发） | 约 950 token/秒（每小时重算约 310 万输入 token，加约 31 万输出 token） |
| L2 撑住 1 小时的门槛，C2 / 3600 | 约 400 token/秒 |
| L2 撑住 5 分钟的门槛，C2 / 300 | 约 4750 token/秒 |
| L2 周转时间上限，C2 / R | 约 25 分钟 |
| L3 每日写入预算 | 约 1.9 TB（3.5 TB 盘，D = 1，份额 0.5） |
| W3_max | b 取 200 KB 时约 110 token/秒 |
| L3 配额（`T_keep` 2 小时） | 约 160 GB，每 rank 约 19 GB |

结论：R 高于 C2 / 3600，按 2.7 这个部署的 1h 档依赖 L3；而 f · R（全部 1h 时约 950 token/秒）远高于 W3_max，所以 1h 档在这个负载下没有完整的容量保障，预算用完后的条目被丢弃。实际影响取决于回访间隔，见 9.3。
