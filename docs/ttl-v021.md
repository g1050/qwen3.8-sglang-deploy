# v0.2.1：状态池与 L3 修复

开发文档，接 [ttl-v020.md](ttl-v020.md)；设计见 [design/ttl-plan1.md](design/ttl-plan1.md)（第六稿）。对外的 TTL 语义和字段与 v0.2.0 相同，本版只改内部的缓存留存。

## 起因

带状态层的模型（本部署是 Mamba 状态）复用一段前缀需要 KV 和状态**同时**在。只有 KV、没有状态，这一段复用不了：匹配会退回到更靠前、状态还在的检查点。v0.2.0 的 TTL 淘汰排序和 L3 写入都只挂在 KV 池上，状态池走自己的 LRU。

实测（`scripts/ttl/eviction_order.py`，约 1000 token 的前缀 700 个，GPU 状态槽耗尽而 KV 还空 24 万 token；先写 1h 的 B 组，再写 5m 的 A 组，时钟拨过 5 分钟后用填充组逼出淘汰）：

| 状态池淘汰方式 | 有效 1h 组的物理复用 | 填充阶段淘汰的状态槽 |
|---|---:|---|
| 原生 LRU（v0.2.0，也是本版默认） | 0% | 有效 166，已过期 1 |
| 只重排队尾 128 个 | 57% | 有效 90，已过期 75 |
| 按租约重排整个池 | 100% | 有效 0，已过期 165 |

另外，约 450 token 的前缀即使紧接着重复请求，物理命中也是 0：太短的前缀没有可恢复的状态检查点。这类请求计费上是命中，实际每次重算。

## 本版改动

### 1. 状态池按租约淘汰（已实现，默认关闭）

状态池不经过可插拔的淘汰策略，而是直接沿 LRU 链表淘汰。做法是在每次状态池淘汰开始前，把链表按"超留存 → 已过期 → 有效"稳定重排（同档保持原 LRU 顺序），GPU 侧和主机侧都做。

**默认关闭**的原因：1 小时的 8 并发压测里，打开它的 3 轮有 2 轮在结束时触发了调度器崩溃（见"已知问题"），没打开的 7 轮有 1 轮。样本很小，四轮 15 分钟的开关对照也都没有崩，所以不能证明是它引起的，但也不能排除。打开方式：`config/cache.json` 的 `ttl.state_pool_lease_order` 置为 `true`。

关闭时的后果只在内部：状态槽紧张时，有效的 1h 条目可能比已过期的先被挤掉，表现为"计费命中但需重算"增多；计费字段不受影响。

### 2. L3 读写（v0.2.0 的 L3 实际读不回数据）

v0.2.0 最后一次调优后只重跑了压测、没有重跑 L3 压力场景，以下缺陷因此漏掉。它们叠加的结果是：写进 L3 的数据几乎都读不回来。

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | 队尾扫描只看当前的叶子。主机淘汰是级联的（叶子走后父节点立刻成为叶子），上层的 prompt 节点从不落盘 | 写一个叶子时连同"淘汰紧接着会轮到"的单子节点祖先一起写 |
| 2 | 一条链只写了头一段。引擎读回一段后要求最后一页带状态，否则整段丢弃 | 整条链要么全写要么不写：从顶部开始连续可写、且以仍有主机状态的节点结尾的最长一段，预算够覆盖才写 |
| 3 | 查盘只说"后面有数据"，没给终点，引擎读到盘上连续数据的末尾，那一页通常没有状态 | 写盘时按引擎自己的页哈希记录"哪些页在盘上、哪些页带状态"；查盘时沿匹配点找连续且已写完的页，截到最后一个带状态的页，把这个终点交给引擎 |
| 4 | 预取策略 `timeout` 会中途截断读盘，截断处没有状态 | 改为 `wait_complete`。现在只在确认盘上有完整数据时才查盘，等待是值得的 |
| 5 | 读回的数据先放进 L2；L2 放不下时引擎保留一个更短的前缀，同样落在非状态页上 | 读回前先为整段腾出 L2 空间，腾不出就只请求放得下且以状态页结尾的部分 |
| 6 | 状态池触发的淘汰不写 L3 | 主机状态池淘汰某个节点的状态前，写入以该节点结尾的路径（需打开第 1 项才生效） |

写盘还在进行中的节点不参与查盘。

验证（`scripts/ttl/l3_stress.py`，正式 L2 容量，160 个约 1.5 万 token 的 1h 前缀，回放最老的 10 个）：5 次查盘，读回 63808 token，4 个前缀完整读回，引擎丢弃 0 次。被淘汰的约 118 万 token 有效 1h 数据里只有 10.9 万（约 9%）写进了 L3，其余因写入预算不足丢弃——这是按磁盘寿命算出的上限（约 111 token/秒），不是缺陷。

压力场景不要再用比 GPU 池还小的 L2：那种配置下 L2 腾不出空间，读回必然被截短，结论没有意义。

### 3. 指标

- `qwen_ttl_evictions_total{pool,layer,lease}`：KV（token）和状态池（槽）在 GPU / 主机两侧的淘汰量，按被淘汰节点的租约状态分。
- `qwen_ttl_host_state_slots{state}`：主机状态池的总槽数和已用槽数（引擎本身不导出）。
- `qwen_ttl_tokens_total` 新增 `l3_skipped_stateless`、`l3_skipped_5m`、`l3_skipped_expiring`、`l3_skipped_no_host_copy`。
- `qwen_ttl_overhead_seconds_total` 新增 `state_order`、`state_tail`。

### 4. 工具

| 脚本 | 用途 |
|---|---|
| `scripts/ttl/eviction_order.py` | 各池是否先淘汰已过期的。短前缀耗尽状态池，长前缀先填满 KV |
| `scripts/ttl/l3_stress.py` | L3 写入、排空后读回 |
| `scripts/ttl/abort_storm.py` | 缓存满载下反复断开客户端连接，检查调度器是否健康 |

诊断开关：`QWEN_TTL_STATE_ORDER`、`QWEN_TTL_DEBUG=1`（打印每条写链和每次查盘）、`QWEN_CACHE_CONFIG=config/cache-l2-only.json`（不加载适配层的对照）。

## 性能

见 [results/README.md](../results/README.md)。5m 档与 baseline 持平；1h 档输出吞吐 −3.2%（v0.2.0 是 −1.0%），差别来自 L3 真正开始写入可读回的完整链。1h 压测一小时里没有发生 L3 读回，所以这一轮只测到了写入的代价、没有测到收益。

## 已知问题

**调度器崩溃（未解决）。** 压测在测量窗口结束、客户端取消在途请求后约 1 秒，引擎的空闲检查报 `pool memory leak detected`（GPU KV 池 available + evictable 比 total 多几千 token），8 个 rank 全部退出。正式服务的容器会自动重启，约 3 分钟不可用，缓存清空。

| 条件 | 出现 / 一小时压测轮数 |
|---|---|
| v0.1.0，无 TTL | 0 / 2 |
| v0.2.0 及其开发期间 | 1 / 7 |
| 打开状态池重排 | 2 / 3 |

- 不是 L3 查盘引起的：其中两次是 5m 流量，没有任何 L3 读写。
- 三个断连场景（`abort_storm.py`，带 TTL 和仅 L2，各断开约 270 个连接）和四轮 15 分钟短压测都没有复现。
- 引擎有开关 `SGLANG_ENABLE_STRICT_MEM_CHECK_DURING_IDLE=0` 可以把这项检查从退出改成告警。没有采用：账目不一致可能意味着显存页被重复释放，继续运行有输出出错的可能。

**其他**

- L3 覆盖率受磁盘寿命预算限制（上面的 9%）。
- 1h 档 TTFT P50 比 baseline 高 24%（平均 +6.3%），单次运行。
- v0.2.0 文档列出的遗留项仍在：L1 / L2 不主动释放超留存数据；显式传 TTL 和混合流量未压测；进程重启后 L3 残留不可复用。
